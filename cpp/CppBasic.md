# Основы C++

## 1. Чем `class` отличается от `struct`?

В C++ `class` и `struct` почти одинаковы. Главное отличие — **уровень доступа по умолчанию**.

### Главное различие

```cpp
struct Person {
    int age;        // public по умолчанию
};

class Person2 {
    int age;        // private по умолчанию
};
```

То есть:

| | `struct` | `class` |
|---|---|---|
| Доступ к членам по умолчанию | `public` | `private` |
| Наследование по умолчанию | `public` | `private` |
| Методы | ✅ | ✅ |
| Конструкторы | ✅ | ✅ |
| Деструкторы | ✅ | ✅ |
| `virtual` | ✅ | ✅ |
| Шаблоны | ✅ | ✅ |

Например:

```cpp
struct Point {
    int x;
    int y;
};

int main() {
    Point p;
    p.x = 10;  // OK
    p.y = 20;  // OK
}
```

А с `class`:

```cpp
class Point {
    int x;
    int y;
};

int main() {
    Point p;
    p.x = 10;  // ОШИБКА: private
}
```

Можно сделать одинаковое поведение явно:

```cpp
class Point {
public:
    int x;
    int y;
};
```

### А что с наследованием?

Здесь тоже есть отличие по умолчанию:

```cpp
struct Base {};

struct A : Base {};  // public наследование

class B : Base {};   // private наследование
```

Но можно явно указать:

```cpp
class B : public Base {};
```

### Как принято использовать?

Обычно соглашение такое:

```cpp
struct Point {
    int x;
    int y;
};
```

`struct` — для простых структур данных, где поля открыты.

```cpp
class BankAccount {
private:
    double balance;

public:
    void deposit(double amount);
    void withdraw(double amount);
};
```

`class` — когда объект имеет скрытое состояние, инварианты и интерфейс.

При этом это именно соглашение, а не требование языка. Технически можно написать полноценный ООП-код через `struct`.

### Если совсем коротко

- `struct` = `public` по умолчанию.
- `class` = `private` по умолчанию.

## 2. Что такое `const`, `constexpr`, `consteval`?

В C++ эти три ключевых слова связаны с неизменяемостью и вычислениями во время компиляции, но смысл у них разный.

### 1. `const` — «нельзя изменить»

```cpp
const int x = 10;

x = 20; // ❌ ошибка
```

`const` гарантирует, что через данное имя значение нельзя изменить.

Например:

```cpp
void print(const std::string& text) {
    // text нельзя изменять
}
```

Здесь `const` особенно полезен, чтобы передавать объект без копирования и при этом гарантировать, что функция его не изменит.

Важно: `const` не означает «значение известно во время компиляции».

```cpp
int getNumber();

const int x = getNumber();
```

`x` нельзя изменить, но его значение определяется во время выполнения.

### 2. `constexpr` — «может быть вычислено во время компиляции»

```cpp
constexpr int x = 10;
constexpr int y = x * 2;
```

Компилятор может вычислить `y` ещё при компиляции.

Можно использовать функции:

```cpp
constexpr int square(int x) {
    return x * x;
}

constexpr int x = square(5); // вычисляется во время компиляции
```

Но интересная особенность: `constexpr` не требует, чтобы функция всегда выполнялась во время компиляции.

```cpp
constexpr int square(int x) {
    return x * x;
}

int n;
std::cin >> n;

int x = square(n); // OK, вычисляется во время выполнения
```

То есть `constexpr` означает примерно:

> «Эту функцию/выражение разрешено вычислять на этапе компиляции, если это возможно».

### 3. `consteval` — «обязательно во время компиляции»

`consteval` появился в C++20.

```cpp
consteval int square(int x) {
    return x * x;
}

consteval int y = square(5); // ✅ вычисляется при компиляции

int n;
std::cin >> n;

int x = square(n); // ❌ ошибка — consteval не может выполняться во время выполнения
```

В отличие от `constexpr`, `consteval` требует:

> «Эта функция обязана выполняться во время компиляции».

Таблица сравнения:

| | `const` | `constexpr` | `consteval` |
|---|---|---|---|
| Смысл | нельзя изменить | может быть вычислено при компиляции | обязано вычисляться при компиляции |
| Время вычисления | выполнение | компиляция или выполнение | только компиляция |
| Год появления | C++98 | C++11 | C++20 |
| Можно использовать с функцией | ✅ (const-метод) | ✅ | ✅ |

### Если совсем коротко

- `const` — «не меняй».
- `constexpr` — «можешь считать на этапе компиляции».
- `consteval` — «считай только на этапе компиляции».

---

Теперь самое запутанное: **указатели и `const`**.

### 1. `const int*` — указатель на константу

```cpp
const int* p = &x;
```

Здесь:

Читается справа налево: `p` — это указатель на `const int`.

```cpp
const int* p;         // указатель на const int

int* const p;         // const указатель на int

const int* const p;   // const указатель на const int
```

Важно: сам `int` нельзя менять, но сам указатель можно.

```cpp
const int x = 10;

const int* p = &x;  // ✅ OK

*p = 20;             // ❌ нельзя менять значение

int y = 30;
p = &y;              // ✅ можно менять сам указатель
```

### 2. `int* const` — const указатель

```cpp
int x = 10;

int* const p = &x;

p = &y;   // ❌ нельзя менять сам указатель

*p = 20;  // ✅ можно менять значение
```

### 3. `const int* const` — и то, и другое

```cpp
const int* const p = &x;

p = &y;   // ❌
*p = 20;  // ❌
```

### Правило чтения

Читай справа налево:

- `int*` — указатель на `int`
- `int* const` — `const` указатель на `int`
- `const int*` — указатель на `const int`
- `const int* const` — `const` указатель на `const int`

Мнемоника:

- `const` стоит перед `*` → `const` относится к данным.
- `const` стоит после `*` → `const` относится к самому указателю.

## 3. Что такое `static` в разных контекстах?

`static` в C++ — одно из тех слов, у которых несколько связанных, но разных смыслов. Лучше разбирать по контексту.

### 1. `static` внутри функции

```cpp
void counter() {
    static int count = 0;
    ++count;
    std::cout << count << '\n';
}
```

Если вызвать:

```cpp
counter(); // 1
counter(); // 2
counter(); // 3
```

Без `static`:

```cpp
void counter() {
    int count = 0;
    ++count;
    std::cout << count << '\n';
}
```

получим:

```text
1
1
1
```

### Что произошло?

Обычная локальная переменная создаётся заново при каждом входе в функцию.

`static`-переменная:

- создаётся один раз;
- живёт до завершения программы;
- сохраняет своё значение между вызовами.

То есть:

```text
обычная локальная:
вызов → создать → использовать → уничтожить
вызов → создать → использовать → уничтожить

static:
программа стартует → создать
вызов → использовать
вызов → использовать
вызов → использовать
программа завершается → уничтожить
```

### 2. `static` у глобальной переменной

```cpp
static int counter = 0;
```

Если это находится на уровне файла:

```cpp
static int counter = 0;
```

то переменная имеет **внутреннее связывание** (internal linkage).

Проще говоря, она доступна только внутри этого `.cpp` файла.

Например:

```cpp
// file1.cpp
static int x = 10;
```

В другом файле:

```cpp
// file2.cpp
extern int x; // ❌ не найдёт тот static x
```

Это используется, чтобы спрятать глобальную переменную от других единиц трансляции.

В современном C++ для ограничения видимости на уровне файла часто предпочитают анонимные `namespace`, а для констант есть нюансы с linkage.

### 3. `static` у функции

Аналогично:

```cpp
static void helper() {
    // ...
}
```

Если функция находится на уровне файла, она доступна только из этого `.cpp` файла.

```cpp
// math.cpp
static void helper() {}
```

Из другого `.cpp` вызвать её нельзя.

Это старый механизм internal linkage.

### 4. `static` у члена класса

Вот здесь начинается самое интересное.

Обычный член:

```cpp
class User {
public:
    int age;
};
```

Каждый объект имеет свою копию `age`:

```cpp
User a;
User b;

a.age = 20;
b.age = 30;
```

Получается:

```text
a → age = 20
b → age = 30
```

А `static`-член:

```cpp
class User {
public:
    static int count;
};
```

имеет одну общую переменную для всего класса.

```text
User
 └── static count
       ↑
       ├── a
       ├── b
       └── c
```

Например:

```cpp
class User {
public:
    static int count;

    User() {
        ++count;
    }
};

int User::count = 0;
```

Теперь:

```cpp
User a;
User b;
User c;

std::cout << User::count; // 3
```

`count` принадлежит не конкретному объекту, а самому классу.

Обращаться можно так:

```cpp
User::count
```

### 5. `static`-метод класса

Можно сделать статическим и метод:

```cpp
class Math {
public:
    static int square(int x) {
        return x * x;
    }
};
```

Вызываем:

```cpp
int x = Math::square(5);
```

без создания объекта:

```cpp
Math m; // не нужен

Math::square(5);
```

### Почему?

Потому что у `static`-метода нет `this`.

Обычный метод:

```cpp
class User {
public:
    void print() {
        std::cout << age;
    }

private:
    int age;
};
```

знает, с каким объектом работает:

```text
user.print()
    ↑
   this
```

А:

```cpp
static void print();
```

не привязан к конкретному объекту.

Поэтому внутри него нельзя напрямую обращаться к обычным полям:

```cpp
class User {
    int age;

public:
    static void print() {
        std::cout << age; // ❌
    }
};
```

Но можно обращаться к `static`-членам:

```cpp
class User {
    static int count;

public:
    static void printCount() {
        std::cout << count; // ✅
    }
};
```

### 6. `static` и наследование

Статический член класса существует в классе, а не отдельно в каждом объекте:

```cpp
class Base {
public:
    static int x;
};

class Derived : public Base {};
```

Можно написать:

```cpp
Base::x = 10;

std::cout << Derived::x;
```

Это тот же самый `x`, а не отдельная копия для `Derived`.

### 7. `static` + `const`

Можно встретить:

```cpp
class Config {
public:
    static const int maxUsers = 100;
};
```

Это означает:

- `static` → одна переменная, принадлежащая классу;
- `const` → её нельзя изменить.

Обращение:

```cpp
Config::maxUsers
```

В современном C++ часто удобнее:

```cpp
class Config {
public:
    static constexpr int maxUsers = 100;
};
```

Здесь значение ещё и является compile-time константой.

### Самое главное

У `static` можно выделить три основных идеи:

**В функции**

```cpp
void foo() {
    static int x;
}
```

Одна переменная, которая сохраняет состояние между вызовами.

**На уровне файла**

```cpp
static int x;
static void foo();
```

Доступно только внутри этого `.cpp` файла.

**В классе**

```cpp
class A {
    static int x;
    static void foo();
};
```

Принадлежит классу, а не отдельному объекту.

Можно запомнить так:

```text
static local variable
        ↓
  живёт всю программу
  и сохраняет состояние

static global/function
        ↓
  только этот .cpp

static class member
        ↓
  один на весь класс
  не один на каждый объект
```

И важное отличие от `const`/`constexpr`:

`static` в первую очередь говорит о времени жизни, linkage или принадлежности классу — в зависимости от контекста. Он сам по себе не означает «константа».

## 4. В чём разница между указателем и ссылкой?

Главная идея:

- **Указатель** (pointer) — это объект, который хранит адрес.
- **Ссылка** (reference) — это другое имя для уже существующего объекта.

Разберём по шагам.

### 1. Указатель

```cpp
int x = 10;

int* p = &x;
```

Здесь:

```text
x = 10
↑
│
p ────┘
```

`p` хранит адрес `x`.

Через указатель можно получить значение:

```cpp
std::cout << *p; // 10
```

И изменить его:

```cpp
*p = 20;

std::cout << x; // 20
```

Но сам указатель тоже можно изменить:

```cpp
int y = 30;

p = &y;
```

Теперь `p` указывает на `y`.

### 2. Ссылка

```cpp
int x = 10;

int& ref = x;
```

`ref` — это ссылка на `x`.

Можно представить:

```text
x
↑
└── ref
```

Теперь:

```cpp
ref = 20;

std::cout << x; // 20
```

`ref` — просто другое имя для `x`.

### 3. Главное отличие: ссылка не может быть null

Указатель может:

```cpp
int* p = nullptr;
```

Это означает:

```text
p сейчас ни на что не указывает.
```

Со ссылкой такой ситуации быть не должно:

```cpp
int& ref = nullptr; // ❌
```

Ссылка должна быть привязана к какому-то объекту при создании.

### 4. Указатель можно переназначить

```cpp
int a = 10;
int b = 20;

int* p = &a;

p = &b; // ✅
```

Теперь `p` указывает на `b`.

А ссылка:

```cpp
int& ref = a;

ref = b;
```

не переназначает ссылку на `b`.

Это очень важный момент.

После:

```cpp
ref = b;
```

происходит примерно:

```cpp
a = b;
```

То есть:

```cpp
int a = 10;
int b = 20;

int& ref = a;

ref = b;

std::cout << a; // 20
```

`ref` всё ещё является ссылкой на `a`.

### 5. Указатель нужно разыменовывать

```cpp
int x = 10;
int* p = &x;

*p = 20;
```

`*p` означает:

> «объект, на который указывает `p`».

Со ссылкой:

```cpp
int& ref = x;

ref = 20;
```

никакого `*` не нужно.

### 6. Ссылки особенно удобны в функциях

Например, хотим изменить переменную:

```cpp
void increment(int& x) {
    ++x;
}

int n = 10;

increment(n);

std::cout << n; // 11
```

Можно сделать через указатель:

```cpp
void increment(int* x) {
    ++(*x);
}

int n = 10;

increment(&n);
```

Работает, но синтаксис сложнее.

Поэтому когда функция обязательно должна получить существующий объект, ссылка часто удобнее.

### 7. Но указатель позволяет выразить «объект может отсутствовать»

Например:

```cpp
void print(int* p) {
    if (p) {
        std::cout << *p;
    }
}
```

Можно вызвать:

```cpp
int x = 10;

print(&x);
print(nullptr);
```

Со ссылкой:

```cpp
void print(int& x);
```

передать `nullptr` нельзя.

### 8. `const` работает с ними немного по-разному

Помнишь предыдущую тему?

```cpp
const int* p;
```

означает:

> через `p` нельзя изменять `int`.

Со ссылкой:

```cpp
const int& ref = x;
```

означает:

> через `ref` нельзя изменять `x`.

Очень распространённый вариант:

```cpp
void print(const std::string& text) {
    std::cout << text;
}
```

Мы не копируем строку и гарантируем, что функция её не изменит.

### Сравнение

| Возможность | Указатель | Ссылка |
|---|---|---|
| Хранит адрес | ✅ | Концептуально ссылается на объект |
| Может быть `nullptr` | ✅ | ❌ |
| Можно переназначить | ✅ | ❌ |
| Нужно разыменование `*` | ✅ | ❌ |
| Можно изменить объект | ✅ | ✅ |
| Нужно инициализировать при создании | ❌ | ✅ |
| Удобен для «может отсутствовать» | ✅ | ❌ |
| Удобен для параметров функций | ✅ | ✅ |

### Очень простая аналогия

Представь квартиру:

```text
Квартира №42
      ↑
      │
   объект x
```

Указатель — это бумажка с адресом:

```text
p → "Квартира №42"
```

Бумажку можно заменить:

```text
p → "Квартира №17"
```

И можно написать:

```text
p → "адрес отсутствует"
```

(`nullptr`).

Ссылка — это второе имя квартиры:

```text
x ──→ Квартира №42
ref ─┘
```

Имя `ref` нельзя потом заставить означать другую квартиру.

### Итого

Запомни четыре вещи:

```cpp
int* p = &x;       // указатель: хранит адрес
int& r = x;        // ссылка: другое имя x

p = &y;             // можно перенаправить
r = y;              // НЕ перенаправляет, а присваивает y → x

p = nullptr;        // можно
// r = nullptr;     // нельзя
```

Практическое правило: если объект обязательно должен существовать — часто используют ссылку. Если объект может отсутствовать или нужно менять, куда указывает переменная — указатель.

## 5. Что такое `nullptr` и чем он лучше `NULL`?

`nullptr` — это специальное значение C++, которое означает:

> «этот указатель никуда не указывает».

Например:

```cpp
int* p = nullptr;
```

Теперь `p` не содержит адрес какого-либо `int`.

### Почему не `NULL`?

В старом C++ часто писали:

```cpp
int* p = NULL;
```

Проблема в том, что `NULL` обычно является не специальным типом, а целочисленным значением вроде `0`:

```cpp
#define NULL 0
```

Из-за этого возникают неоднозначности.

Например:

```cpp
void foo(int x) {
    std::cout << "int\n";
}

void foo(int* p) {
    std::cout << "pointer\n";
}
```

Вызов:

```cpp
foo(NULL);
```

может выбрать версию с `int`, потому что `NULL` — фактически `0`.

А:

```cpp
foo(nullptr);
```

однозначно выбирает:

```cpp
foo(int*);
```

потому что `nullptr` специально предназначен для указателей.

### Что такое `nullptr` технически?

У него есть специальный тип:

```cpp
std::nullptr_t
```

Он был добавлен в C++11.

При этом `nullptr` можно преобразовать в любой обычный указательный тип:

```cpp
int* p = nullptr;
double* d = nullptr;
std::string* s = nullptr;
```

Но `nullptr` — не обычный `int`.

```cpp
int x = nullptr; // ❌
```

### Очень важный момент

Нельзя разыменовывать `nullptr`:

```cpp
int* p = nullptr;

std::cout << *p; // 💥 неопределённое поведение
```

Сначала нужно проверить:

```cpp
if (p != nullptr) {
    std::cout << *p;
}
```

Причём обычно пишут ещё короче:

```cpp
if (p) {
    std::cout << *p;
}
```

И наоборот:

```cpp
if (!p) {
    std::cout << "Pointer is null";
}
```

### Сравнение

| | `NULL` | `nullptr` |
|---|---|---|
| Старый подход | ✅ | |
| C++11+ | Работает, но устаревший стиль | ✅ |
| Специальный тип | ❌ | `std::nullptr_t` |
| Явно предназначен для указателей | ❌ | ✅ |
| Может вызвать неоднозначность с `int` | ✅ | ❌ |
| Рекомендуется в современном C++ | ❌ | ✅ |

### Запомни

```cpp
int* p = nullptr;  // ✅ современный C++
int* p = NULL;     // ⚠️ старый стиль
int* p = 0;        // ⚠️ тоже старый стиль
```

`nullptr` лучше `NULL`, потому что компилятор понимает: это именно «нулевой указатель», а не просто число `0`.

## 6. Что такое `lvalue`, `rvalue`, `xvalue`?

Это одна из самых важных и одновременно самых запутанных тем в C++. Главное — не пытаться запомнить определения из стандарта, а сначала понять интуитивно.

### 1. `lvalue`

Упрощённо:

> `lvalue` — выражение, которое обозначает конкретный объект, у которого есть устойчивое местоположение.

Например:

```cpp
int x = 10;

x = 20;
```

`x` — `lvalue`.

Его можно представить как «имя ячейки памяти»:

```text
x
↓
┌────┐
│ 10 │
└────┘
```

Поэтому можно взять его адрес:

```cpp
int* p = &x; // ✅
```

Другие примеры `lvalue`:

```cpp
int x;

x

*p

arr[0]

obj.field
```

### 2. `rvalue`

Упрощённо:

> `rvalue` — временное значение, которое обычно не является именованным объектом, с которым мы собираемся работать дальше.

Например:

```cpp
int x = 10 + 20;
```

Здесь:

```text
10 + 20
```

даёт временное значение `30`.

Оно не имеет собственного имени:

```text
10 + 20
   ↓
  30
```

Поэтому:

```cpp
int* p = &(10 + 20); // ❌
```

нельзя.

Другие примеры:

```cpp
42

x + y

foo()        // если возвращает значение

std::string("hello")
```

### 3. Почему они называются `lvalue` и `rvalue`?

Исторически:

```cpp
x = 10;
```

`x` находится слева (left), а `10` справа (right).

Отсюда старое упрощённое объяснение:

- `lvalue` → left value
- `rvalue` → right value

Но это уже не совсем корректно.

Например:

```cpp
x = y;
```

`y` находится справа, но `y` — `lvalue`.

Поэтому лучше запомнить не «слева/справа», а:

- `lvalue` → существующий объект, к которому можно обратиться
- `rvalue` → временное/перемещаемое значение

### 4. А где тут `xvalue`?

Вот здесь начинается C++11 и move semantics.

`xvalue` можно воспринимать как:

> существующий объект, который мы разрешаем "забрать"/переместить.

Например:

```cpp
std::string a = "hello";

std::move(a);
```

`std::move(a)` — это `xvalue`.

Сам `a` никуда не исчез:

```text
a
↓
┌─────────┐
│ "hello" │
└─────────┘
```

Но `std::move(a)` говорит:

> «С этим объектом теперь можно обращаться как с временным и переместить из него ресурсы».

Например:

```cpp
std::string a = "Hello";

std::string b = std::move(a);
```

Здесь конструктор `b` может использовать move constructor, вместо копирования строки.

### 5. Самая полезная схема

В современном C++ есть более широкие категории:

```text
                 expression
                     │
          ┌──────────┴──────────┐
          │                     │
        glvalue                rvalue
          │                     │
     ┌────┴────┐          ┌─────┴─────┐
     │         │          │           │
  lvalue    xvalue    prvalue      ...
```

Точнее:

```text
glvalue
├── lvalue
└── xvalue

rvalue
├── xvalue
└── prvalue
```

То есть `xvalue` одновременно является `glvalue` и `rvalue`.

Это звучит странно, но становится понятнее на примере:

```text
                 выражения
                     │
          ┌──────────┴──────────┐
        glvalue                rvalue
          │                     │
     ┌────┴────┐          ┌─────┴─────┐
     │         │          │           │
  lvalue    xvalue     xvalue      prvalue
```

`xvalue` находится на пересечении.

### 6. Что такое `prvalue`?

Мы пока его не упоминали, но без него картина неполная.

`prvalue` — это примерно:

> чистое временное значение.

Например:

```cpp
42
```

или:

```cpp
x + y
```

или:

```cpp
std::string("hello")
```

В отличие от `xvalue`, у `prvalue` нет уже существующего объекта, из которого мы «забираем» ресурсы.

Сравни:

```cpp
std::string("hello")  // prvalue
std::move(a)          // xvalue
```

### 7. Самое интересное — ссылки

Именно для этого всё обычно и изучают.

**lvalue-ссылка**

```cpp
int x = 10;

int& a = x;     // ✅
int& b = 20;    // ❌
```

Обычная ссылка `T&` может привязаться к `lvalue`.

**const lvalue-ссылка**

```cpp
const int& a = x;  // ✅
const int& b = 20; // ✅
```

`const T&` может привязываться и к временным значениям.

**rvalue-ссылка**

```cpp
int&& a = 20; // ✅
```

`T&&` предназначена для работы с `rvalue`:

```cpp
int x = 10;

int&& a = x;            // ❌
int&& b = std::move(x); // ✅
```

И именно `T&&` лежит в основе move semantics и perfect forwarding.

### 8. Почему `std::move` не перемещает сам по себе?

Это очень важный нюанс.

```cpp
std::string a = "Hello";

std::move(a);
```

`std::move` ничего не перемещает.

Он фактически говорит компилятору:

> «Рассматривай `a` как rvalue/xvalue».

А уже затем, например, move constructor может воспользоваться этим:

```cpp
std::string b = std::move(a);
```

То есть:

```text
a
│
│ std::move
▼
xvalue
│
│ move constructor
▼
b
```

### 9. Как различать на практике

Возьми:

```cpp
int x = 10;
int y = 20;
```

- `x` → lvalue
- `x + y` → prvalue
- `std::move(x)` → xvalue
- `42` → prvalue
- `*p` → lvalue

```cpp
int foo() {
    return 42;
}
```

то:

- `foo()` → prvalue

### Короткая шпаргалка

**`lvalue`** — «Вот конкретный существующий объект»

```cpp
int x;
x              ← lvalue
*p             ← lvalue
arr[0]         ← lvalue
```

**`prvalue`** — «Вот новое/временное значение»

```cpp
42             ← prvalue
x + y          ← prvalue
foo()          ← обычно prvalue при возврате по значению
```

**`xvalue`** — «Вот существующий объект, который можно использовать как временный / из которого можно переместить ресурсы»

```cpp
std::move(x)   ← xvalue
```

А самое важное для дальнейшего изучения C++:

- `lvalue` → `T&`
- `rvalue` → `T&&`

и:

```cpp
void foo(int&);   // принимает lvalue
void foo(int&&);  // принимает rvalue
```

Например:

```cpp
int x = 10;

foo(x);            // вызовет foo(int&)
foo(10);           // вызовет foo(int&&)
foo(std::move(x)); // вызовет foo(int&&)
```

Если ты сейчас изучаешь C++ с нуля, я бы следующим шагом разобрал `T&` и `T&&` на реальных примерах — именно там lvalue/rvalue/xvalue наконец начинают иметь практический смысл.

## 7. Что такое perfect forwarding?

Perfect forwarding — это механизм C++, который позволяет шаблонной функции передать аргумент дальше, сохранив его исходную категорию: был аргумент `lvalue` — останется `lvalue`, был `rvalue` — останется `rvalue`.

Это нужно прежде всего для обёрток, фабрик и generic-кода.

### 1. Проблема

Представим:

```cpp
void process(const std::string& s) {
    std::cout << "lvalue/const\n";
}

void process(std::string&& s) {
    std::cout << "rvalue\n";
}
```

Напрямую:

```cpp
std::string name = "Bob";

process(name);              // lvalue
process(std::string("Bob")); // rvalue
```

Всё хорошо.

Но если мы сделаем обычную обёртку:

```cpp
void wrapper(std::string&& s) {
    process(s);
}
```

то:

```cpp
wrapper(std::string("Bob"));
```

внутри `wrapper` переменная `s` — `lvalue`!

То есть исходно было:

```text
rvalue
  ↓
wrapper
  ↓
s становится lvalue
```

И `process(s)` уже не видит исходный `rvalue`.

### 2. `std::forward` решает проблему

Пишем шаблон:

```cpp
template <typename T>
void wrapper(T&& value) {
    process(std::forward<T>(value));
}
```

Теперь:

```cpp
std::string name = "Bob";

wrapper(name);               // передали lvalue
wrapper(std::string("Bob")); // передали rvalue
```

`std::forward` сохраняет исходную категорию.

```text
wrapper(name)
    ↓
   lvalue
    ↓
forward<T>
    ↓
   lvalue


wrapper(std::string("Bob"))
    ↓
   rvalue
    ↓
forward<T>
    ↓
   rvalue
```

### 3. Но почему `T&&` принимает и lvalue, и rvalue?

Вот это ключевой момент.

```cpp
template <typename T>
void wrapper(T&& value)
```

В таком контексте `T&&` — это **forwarding reference** (раньше часто говорили universal reference).

Передали `lvalue`:

```cpp
std::string name;

wrapper(name);
```

Компилятор выводит:

```cpp
T = std::string&
```

И получается:

```text
T&&
↓
std::string& &&
```

По специальному правилу схлопывания ссылок:

```text
T&  && → T&
T&  &  → T&
T&& &  → T&
T&& && → T&&
```

Поэтому параметр становится:

```cpp
std::string&
```

Передали `rvalue`:

```cpp
wrapper(std::string("Bob"));
```

Тогда:

```cpp
T = std::string
```

и:

```text
T&&
↓
std::string&&
```

То есть:

```text
lvalue → T = T&   → параметр T&
rvalue → T = T    → параметр T&&
```

### 4. Зачем тогда `std::forward`?

Вот здесь самая важная тонкость.

Даже если параметр имеет тип:

```cpp
T&& value
```

само выражение `value` является `lvalue`, потому что у него есть имя.

Например:

```cpp
template <typename T>
void wrapper(T&& value) {
    process(value); // value — lvalue!
}
```

Поэтому нужен:

```cpp
process(std::forward<T>(value));
```

`std::forward` говорит:

> «Верни `value` в той категории, в которой исходный аргумент пришёл в функцию».

### 5. Perfect forwarding на простом примере

```cpp
void process(int&) {
    std::cout << "lvalue\n";
}

void process(int&&) {
    std::cout << "rvalue\n";
}

template <typename T>
void wrapper(T&& value) {
    process(std::forward<T>(value));
}
```

Теперь:

```cpp
int x = 10;

wrapper(x);
```

получим:

```text
lvalue
```

А:

```cpp
wrapper(42);
```

получим:

```text
rvalue
```

И:

```cpp
wrapper(std::move(x));
```

тоже:

```text
rvalue
```

### 6. Типичный реальный пример — `std::make_unique`

Perfect forwarding постоянно используется в стандартной библиотеке.

Например:

```cpp
auto p = std::make_unique<MyClass>(10, "hello");
```

Условно внутри происходит что-то вроде:

```cpp
template <typename T, typename... Args>
std::unique_ptr<T> make_something(Args&&... args) {
    return new T(std::forward<Args>(args)...);
}
```

Здесь `Args&&...` принимает любое количество аргументов, а:

```cpp
std::forward<Args>(args)...
```

передаёт их дальше, сохраняя lvalue/rvalue каждого аргумента.

### 7. `std::move` и `std::forward` — не одно и то же

Это очень важно.

**`std::move`**

Грубо говоря:

> «Я разрешаю рассматривать этот объект как rvalue».

```cpp
std::move(x)
```

всегда превращает выражение в `xvalue`.

**`std::forward`**

Грубо говоря:

> «Если изначально это был rvalue — оставь rvalue. Если lvalue — оставь lvalue».

```cpp
std::forward<T>(x)
```

используется преимущественно внутри шаблонов.

Визуально:

```text
                 аргумент
                    │
          ┌─────────┴─────────┐
          │                   │
       lvalue                rvalue
          │                   │
          ▼                   ▼
       wrapper<T>          wrapper<T>
          │                   │
          └─────────┬─────────┘
                    │
              std::forward<T>
                    │
          ┌─────────┴─────────┐
          │                   │
       lvalue                rvalue
          │                   │
          ▼                   ▼
       функция             функция
```

### Главное, что нужно запомнить

```cpp
template <typename T>
void wrapper(T&& value) {
    foo(std::forward<T>(value));
}
```

Это и есть классический паттерн perfect forwarding:

- `T&&` принимает и lvalue, и rvalue.
- `T` выводится по-разному для них.
- Именованный `value` сам по себе становится lvalue.
- `std::forward<T>(value)` восстанавливает исходную категорию.
- `foo` получает аргумент так, как будто `wrapper` вообще не было.

Именно поэтому perfect forwarding особенно важен для понимания `T&&`, вывода шаблонных типов и reference collapsing.

## 8. Чем `std::unique_ptr` отличается от `std::shared_ptr`?

Коротко:

- `std::unique_ptr` — владелец один.
- `std::shared_ptr` — владельцев может быть несколько.

И это напрямую связано с тем, что мы только что обсуждали: указатели, `nullptr`, move и perfect forwarding.

### 1. `unique_ptr` — единственный владелец

```cpp
std::unique_ptr<int> p = std::make_unique<int>(42);
```

`p` владеет объектом:

```text
p
│
▼
┌──────┐
│  42  │
└──────┘
```

Когда `p` уничтожается, объект тоже уничтожается:

```cpp
{
    auto p = std::make_unique<int>(42);
} // здесь int автоматически удаляется
```

Главное свойство — копировать `unique_ptr` нельзя:

```cpp
auto p1 = std::make_unique<int>(42);

auto p2 = p1; // ❌
```

Почему? Потому что тогда было бы два владельца.

Но можно переместить владение:

```cpp
auto p1 = std::make_unique<int>(42);

auto p2 = std::move(p1); // ✅
```

Теперь:

```text
p1 → nullptr

p2 ─────→ [42]
           ↑
        единственный
          владелец
```

Это как раз применение move semantics.

### 2. `shared_ptr` — совместное владение

```cpp
auto p1 = std::make_shared<int>(42);
auto p2 = p1;
```

Теперь оба указателя владеют одним объектом:

```text
p1 ──┐
     ├──→ [42]
p2 ──┘
```

Внутри используется счётчик ссылок (reference count).

После:

```cpp
auto p1 = std::make_shared<int>(42);
```

примерно:

```text
объект
 ↑
 │
count = 1
```

После:

```cpp
auto p2 = p1;
```

получаем:

```text
объект
 ↑
 │
count = 2
```

Когда `p2` уничтожается:

```text
count = 1
```

Когда уничтожается последний `shared_ptr`:

```text
count = 0
    ↓
объект удаляется
```

### 3. Главное различие

```cpp
auto u1 = std::make_unique<int>(10);

// auto u2 = u1;          // ❌ копирование запрещено
auto u2 = std::move(u1); // ✅ передача владения
```

А `shared_ptr`:

```cpp
auto s1 = std::make_shared<int>(10);
auto s2 = s1; // ✅ совместное владение
```

### 4. `unique_ptr` обычно предпочтительнее

Если тебе не нужно несколько владельцев, лучше использовать:

```cpp
std::unique_ptr
```

Например:

```cpp
class User {
    std::unique_ptr<Database> database;
};
```

`User` единолично владеет `Database`.

Нет смысла использовать `shared_ptr`, если владение должно быть однозначным:

```cpp
std::shared_ptr<Database> // зачем?
```

`unique_ptr`:

- проще;
- дешевле;
- не имеет счётчика ссылок;
- явно показывает единственного владельца;
- легко перемещается.

### 5. У `shared_ptr` есть дополнительная стоимость

При использовании:

```cpp
std::shared_ptr<T>
```

нужно поддерживать control block, где хранится, среди прочего, счётчик владельцев.

Упрощённо:

```text
shared_ptr
   │
   ├───────────────→ объект
   │
   └───────────────→ control block
                         │
                      count = 3
```

Поэтому `shared_ptr` обычно тяжелее `unique_ptr`.

При этом конкретная стоимость зависит от реализации и сценария использования.

### 6. `make_shared` и `make_unique`

Обычно объекты создают так:

```cpp
auto p = std::make_unique<MyClass>(10, "Bob");
```

и:

```cpp
auto p = std::make_shared<MyClass>(10, "Bob");
```

А не:

```cpp
std::unique_ptr<MyClass>(
    new MyClass(10, "Bob")
);
```

или:

```cpp
std::shared_ptr<MyClass>(
    new MyClass(10, "Bob")
);
```

`make_*` безопаснее и удобнее, а для `make_shared` ещё часто позволяет эффективно разместить объект и control block вместе.

### 7. А что насчёт `weak_ptr`?

Вот здесь появляется третий важный тип:

```cpp
std::weak_ptr
```

Он не владеет объектом.

Например:

```text
shared_ptr ──┐
             ├──→ объект
shared_ptr ──┘
   ↑
weak_ptr
```

`weak_ptr` используется, когда нужно наблюдать за объектом, но не продлевать его жизнь.

Особенно важно для решения проблемы циклических ссылок:

```text
A ──shared_ptr──→ B
↑                │
└────shared──────┘
```

Такой цикл может привести к тому, что объекты никогда не уничтожатся.

### Очень важная практическая схема

Представь вопрос:

> «Кто владеет этим объектом?»

**Ответ: один конкретный объект**

Используй:

```cpp
std::unique_ptr<T>
```

**Ответ: несколько объектов должны совместно владеть им**

Используй:

```cpp
std::shared_ptr<T>
```

**Ответ: мне нужно только наблюдать и не владеть**

Используй:

```cpp
std::weak_ptr<T>
```

### Шпаргалка

```text
unique_ptr
    │
    └── 1 владелец
        ↓
      move
        ↓
    владение передаётся


shared_ptr
    │
    └── N владельцев
        ↓
    reference count
        ↓
    последний владелец
        ↓
      delete


weak_ptr
    │
    └── 0 владельцев
        ↓
    просто наблюдает
```

И хорошее правило современного C++:

Сначала думай об обычном объекте → если нужна динамическая lifetime-владение, `unique_ptr` → `shared_ptr` только когда действительно нужно совместное владение.

Не стоит выбирать `shared_ptr` просто потому, что «так безопаснее»: он решает другую задачу — shared ownership.

## 9. Когда возникает dangling pointer/reference?

Dangling pointer/reference — это указатель или ссылка, которые ссылаются на объект, которого уже не существует.

Это одна из самых опасных ошибок в C++: обращение через них приводит к undefined behavior (UB).

### 1. Указатель после `delete`

```cpp
int* p = new int(42);

delete p;

std::cout << *p; // ❌ dangling pointer
```

После `delete` память освобождена, но `p` всё ещё содержит старый адрес:

До `delete`:

```text
p ─────→ [42]
```

После `delete`:

```text
p ─────→ ???   ← объект больше не существует
```

Хорошая привычка:

```cpp
delete p;
p = nullptr;
```

### 2. Указатель на локальную переменную

```cpp
int* getPointer() {
    int x = 42;
    return &x; // ❌
}
```

После завершения функции `x` уничтожается.

```cpp
int* p = getPointer();

std::cout << *p; // ❌ dangling pointer
```

Получается:

```text
getPointer():

x ──→ [42]

функция завершилась
       ↓
x уничтожен

p ──→ ???
```

### 3. Dangling reference

Ссылка тоже может стать висячей:

```cpp
int& getReference() {
    int x = 42;
    return x; // ❌
}
```

Затем:

```cpp
int& r = getReference();

std::cout << r; // ❌
```

`r` ссылается на уже уничтоженный `x`.

### 4. После удаления объекта через `unique_ptr`

```cpp
auto p = std::make_unique<int>(42);

int* raw = p.get();

p.reset();

std::cout << *raw; // ❌ dangling pointer
```

`raw` не владеет объектом. Когда `unique_ptr` удалил объект, `raw` стал dangling pointer.

Это хороший пример того, почему сырой указатель не гарантирует время жизни объекта.

### 5. `shared_ptr` помогает с этим

```cpp
auto p = std::make_shared<int>(42);

auto q = p;

p.reset();

std::cout << *q; // ✅
```

Почему?

Потому что `q` всё ещё владеет объектом:

```text
p ──→ объект ←── q
       ↑
    count = 2

p.reset()

q ──→ объект
       ↑
    count = 1
```

Объект будет уничтожен только после исчезновения последнего `shared_ptr`.

### 6. Но `weak_ptr` как раз может стать «устаревшим»

```cpp
auto shared = std::make_shared<int>(42);
std::weak_ptr<int> weak = shared;

shared.reset();
```

Теперь объект уничтожен.

Поэтому нельзя просто разыменовать `weak_ptr`. Нужно:

```cpp
if (auto p = weak.lock()) {
    std::cout << *p;
} else {
    std::cout << "Объект уже уничтожен";
}
```

### Ещё один частый случай — контейнеры

Например:

```cpp
std::vector<int> v = {1, 2, 3};

int* p = &v[0];

v.push_back(4);

std::cout << *p; // ⚠️ может быть dangling
```

Почему? `vector` мог перераспределить память при `push_back`, и старый адрес `v[0]` больше не действителен.

### Как избежать dangling pointer/reference

Главный принцип:

> Следи за временем жизни объекта, на который ссылаешься.

Часто помогают:

- `std::unique_ptr` — явное единоличное владение;
- `std::shared_ptr` — совместное владение;
- `std::weak_ptr` — безопасное наблюдение за объектом;
- ссылки/указатели только тогда, когда гарантирована жизнь объекта;
- после `delete` не использовать указатель;
- осторожно хранить указатели/ссылки на элементы `vector`, `string` и других контейнеров, которые могут перераспределять память.

### Самая короткая формула

```text
объект существует
      ↓
pointer/reference
      ↓
объект уничтожен
      ↓
dangling pointer/reference
      ↓
обращение к нему → Undefined Behavior ❌
```

И важный нюанс: `nullptr` не является dangling pointer. `nullptr` означает «ни на что не указывает», а dangling pointer содержит адрес, который раньше был действительным, но больше им не является.

## 10. Что такое RAII?

RAII (Resource Acquisition Is Initialization) — один из фундаментальных принципов C++.

Идея очень простая:

> Ресурс принадлежит объекту, а время жизни ресурса связано со временем жизни этого объекта.

- Когда объект создаётся → ресурс захватывается.
- Когда объект уничтожается → ресурс автоматически освобождается.

Именно на RAII построены `std::unique_ptr`, `std::shared_ptr`, `std::lock_guard`, `std::fstream` и многие другие классы стандартной библиотеки.

### 1. Проблема без RAII

Представим ручное управление памятью:

```cpp
void foo() {
    int* p = new int(42);

    // работа...

    delete p;
}
```

Пока всё хорошо.

Но если между `new` и `delete` возникнет исключение:

```cpp
void foo() {
    int* p = new int(42);

    doSomething(); // 💥 может бросить исключение

    delete p;
}
```

`delete` может не выполниться.

Получаем утечку памяти.

### 2. RAII решает проблему

Используем `std::unique_ptr`:

```cpp
void foo() {
    auto p = std::make_unique<int>(42);

    doSomething();
}
```

Что произойдёт:

```text
foo()
  │
  ├── создаём p
  │      ↓
  │    [42]
  │
  ├── doSomething()
  │
  └── выход из функции
          ↓
      p уничтожается
          ↓
      объект удаляется
```

Даже если `doSomething()` бросит исключение:

```cpp
void foo() {
    auto p = std::make_unique<int>(42);

    doSomething(); // 💥 exception

} // p всё равно уничтожается
```

Деструктор `unique_ptr` автоматически освободит ресурс.

Это и есть RAII.

### 3. RAII — не только про память

Это очень важно.

Ресурсом может быть практически всё, что нужно освободить или вернуть:

- динамическая память;
- файл;
- mutex;
- сетевое соединение;
- сокет;
- дескриптор ОС;
- транзакция;
- GPU-ресурс и т. д.

Например, файл:

```cpp
{
    std::ofstream file("data.txt");

    file << "Hello";
}
```

Когда `file` выходит из области видимости, его деструктор закрывает файл.

Не нужно:

```cpp
file.close();
```

вручную в обычном сценарии.

### 4. RAII + mutex

Очень хороший пример:

```cpp
std::mutex mutex;

void foo() {
    std::lock_guard<std::mutex> lock(mutex);

    // критическая секция
}
```

Что происходит:

```text
создание lock_guard
        ↓
   mutex.lock()
        ↓
работаем с ресурсом
        ↓
lock_guard уничтожается
        ↓
   mutex.unlock()
```

Даже если внутри будет исключение:

```cpp
void foo() {
    std::lock_guard<std::mutex> lock(mutex);

    doSomething(); // exception
} // mutex автоматически освобождается
```

### 5. Почему это называется RAII?

Название историческое и немного сбивает с толку.

> Resource Acquisition Is Initialization

То есть:

> «Получение ресурса происходит при инициализации объекта».

Например:

```cpp
auto p = std::make_unique<int>(42);
```

Создание `p` → получение владения объектом.

А затем:

```text
p уничтожается
      ↓
ресурс освобождается
```

Поэтому часто формулируют проще:

> Constructor acquires, destructor releases.

Конструктор получает ресурс, деструктор освобождает.

### 6. Связь с тем, что мы уже изучили

Ты уже видел несколько примеров RAII:

**`unique_ptr`**

```cpp
std::unique_ptr<int> p;
```

Владеет памятью и освобождает её в деструкторе.

**`shared_ptr`**

```cpp
std::shared_ptr<int> p;
```

Управляет временем жизни объекта через reference counting.

**`weak_ptr`**

Не владеет ресурсом, поэтому сам объект не удерживает.

**Обычный объект**

```cpp
{
    MyClass obj;
}
```

При выходе из `{}` вызывается:

```cpp
obj.~MyClass();
```

И это фундаментальный механизм RAII.

### 7. Самая важная идея C++

RAII позволяет писать:

```cpp
void foo() {
    Resource resource;

    // работаем с resource

} // ресурс автоматически освобождён
```

вместо:

```cpp
void foo() {
    Resource* resource = acquire();

    // работаем...

    release(resource);
}
```

Вторая версия опаснее, потому что нужно помнить про каждый возможный путь выхода:

- обычный `return`
- exception
- ранний `return`
- `break`
- `continue`
- ...

RAII переносит ответственность с программиста на деструктор объекта.

### Запомни одну формулу

```text
RAII

создание объекта
      ↓
получение ресурса
      ↓
работа
      ↓
выход из scope
      ↓
деструктор
      ↓
освобождение ресурса
```

Именно поэтому в современном C++ хорошее правило звучит примерно так:

> Не управляй ресурсами вручную, если можно завернуть их в RAII-объект.

Отсюда следует очень важная практика: `new`/`delete` в пользовательском коде нужны гораздо реже, чем может показаться новичку.

## 11. Что такое UB (undefined behavior)? Приведите примеры.

UB (Undefined Behavior) — это неопределённое поведение программы.

В C++ это означает, что программа сделала то, что стандарт языка не определяет, что должно произойти дальше.

И тут важный момент:

> UB — это не обязательно "программа упадёт".

Она может:

- упасть;
- вывести странное значение;
- «работать нормально»;
- работать по-разному в Debug и Release;
- после оптимизации компилятора вести себя совершенно неожиданно.

Компилятор вправе предполагать, что UB в корректной программе не происходит, и оптимизировать код исходя из этого.

### 1. Разыменование `nullptr`

Мы уже разбирали `nullptr`:

```cpp
int* p = nullptr;

std::cout << *p; // UB
```

`p` никуда не указывает, поэтому попытка получить `*p` — UB.

### 2. Выход за границы массива

```cpp
int arr[3] = {10, 20, 30};

std::cout << arr[5]; // UB
```

Допустимые индексы:

```text
arr[0] → 10
arr[1] → 20
arr[2] → 30
```

`arr[5]` находится за пределами массива.

### 3. Использование объекта после `delete`

```cpp
int* p = new int(42);

delete p;

std::cout << *p; // UB
```

После `delete` объект уничтожен.

`p` теперь является dangling pointer — висячим указателем.

Это напрямую связано с предыдущей темой:

```text
delete
  ↓
объект уничтожен
  ↓
p всё ещё содержит старый адрес
  ↓
*p
  ↓
UB
```

### 4. Возврат ссылки на локальную переменную

```cpp
int& getValue()
{
    int x = 42;
    return x;
}
```

После выхода из `getValue()` переменная `x` уничтожается.

Полученная ссылка становится dangling reference.

Например:

```cpp
int& ref = getValue();

std::cout << ref; // UB
```

### 5. Деление на ноль

Для целых чисел:

```cpp
int x = 10;
int y = 0;

std::cout << x / y; // UB
```

В отличие от floating-point арифметики, целочисленное деление на ноль в C++ — UB.

### 6. Signed integer overflow

Это особенно важный пример.

```cpp
int x = std::numeric_limits<int>::max();

x = x + 1; // UB
```

Для `int` переполнение знакового целого типа — UB.

Это отличается от `unsigned`:

```cpp
unsigned int x = UINT_MAX;

x = x + 1; // определённое поведение: становится 0
```

### 7. Использование неинициализированной переменной

Например:

```cpp
int x;

std::cout << x;
```

`x` не был инициализирован.

Использование значения такой переменной может приводить к UB (с некоторыми нюансами стандарта и конкретного типа/контекста).

Правильно:

```cpp
int x = 0;
```

### 8. Нарушение правил работы с объектами

Например, можно получить UB, если обращаться к объекту через указатель неподходящего типа, нарушая правила aliasing/object lifetime.

Упрощённый пример:

```cpp
float f = 3.14f;

int* p = reinterpret_cast<int*>(&f);

std::cout << *p; // UB
```

Нельзя просто взять объект одного типа и интерпретировать его как другой объект через обычное разыменование такого указателя.

### Почему UB особенно опасен?

Представим:

```cpp
bool foo(int x)
{
    if (x > 0)
        return true;

    return false;
}
```

Компилятор может делать предположения о корректной программе.

А если где-то возникает UB, например:

```cpp
int x = INT_MAX;
x++;
```

нельзя рассуждать:

> «Ну, наверное, `x` станет `INT_MIN`».

Для signed overflow C++ ничего такого не гарантирует.

### UB vs ошибка

Это полезно различать:

```text
Ошибка компиляции
       ↓
программа не компилируется

Runtime error
       ↓
программа запустилась, но произошла ошибка

Undefined Behavior
       ↓
стандарт C++ не определяет, что должна делать программа
```

Именно поэтому UB может быть очень коварным.

### Самые важные примеры, которые стоит запомнить

```cpp
*p;                  // p == nullptr → UB

arr[100];            // за пределами массива → UB

*p;                  // p после delete → UB

return local;        // ссылка на уничтоженный объект → UB

10 / 0;              // integer division by zero → UB

INT_MAX + 1;         // signed overflow → UB
```

И ещё важная связь с предыдущими темами:

dangling pointer/reference → очень часто источник UB.

А RAII + smart pointers помогают существенно уменьшить количество таких ошибок.
