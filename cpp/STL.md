# STL

Это очень важный вопрос для C++: на собеседовании обычно хотят понимать, какая структура данных стоит под контейнером, где лежат элементы и какая сложность основных операций.

Сначала коротко:

| Контейнер | Внутри | Доступ | Поиск | Вставка |
|-----------|--------|--------|-------|---------|
| `vector` | динамический массив | O(1) | O(n) | O(1) в конец амортизированно |
| `list` | двусвязный список | O(n) | O(n) | O(1) по итератору |
| `map` | сбалансированное дерево | O(log n) | O(log n) | O(log n) |
| `unordered_map` | хеш-таблица | — | O(1) в среднем | O(1) в среднем |

Теперь разберём, что реально находится внутри.

## 1. Как устроены `std::vector`, `std::list`, `std::map`, `std::unordered_map`?

### `std::vector`

`vector` — это динамический массив.

Упрощённо внутри:

```text
vector
 ┌───────────────────────────────┐
 │ 10 │ 20 │ 30 │ 40 │ свободно │
 └───────────────────────────────┘
 ↑
 contiguous memory
```

Элементы лежат подряд в памяти.

Например:

```cpp
std::vector<int> v = {10, 20, 30, 40};
```

В памяти примерно:

```text
адрес
1000 → 10
1004 → 20
1008 → 30
1012 → 40
```

Для `int` условно по 4 байта.

Поэтому `v[2]` очень быстро вычисляется:

```cpp
address = начало + 2 * sizeof(int);
```

Отсюда `v[i] → O(1)`.

### `std::list`

`std::list` — это двусвязный список.

Вместо одного непрерывного массива элементы находятся в отдельных узлах.

Упрощённо:

```text
nullptr
   ↑
   │
[prev | 10 | next]
              ↓
        [prev | 20 | next]
                         ↓
                   [prev | 30 | next]
                                      ↓
                                   nullptr
```

Каждый узел хранит примерно:

```cpp
struct Node {
    Node* prev;
    T value;
    Node* next;
};
```

Поэтому элементы могут находиться в совершенно разных местах памяти.

**Почему `list` не имеет быстрого `operator[]`?**

Если у нас `list[100]`, чтобы найти 100-й элемент, нужно пройти:

```text
0 → 1 → 2 → 3 → ... → 100
```

Поэтому доступ — `O(n)`. В отличие от `vector[100]`, где можно сразу вычислить адрес → `O(1)`.

**Зато вставка может быть очень быстрой**

Если у нас есть итератор:

```cpp
auto it = ...;
list.insert(it, 42);
```

можно просто переставить несколько указателей:

```text
до:     A ↔ B
после:  A ↔ NEW ↔ B
```

Поэтому вставка/удаление по известному итератору — `O(1)`. Но поиск места для вставки может стоить `O(n)`.

### `std::map`

`std::map` обычно реализован на основе сбалансированного бинарного дерева поиска, как правило, красно-чёрного дерева.

Упрощённо:

```text
             50
            /  \
          30    70
         / \    / \
       20  40  60  80
```

В `map` хранятся пары:

```cpp
std::map<int, std::string> m;

m[10] = "Alice";
m[20] = "Bob";
m[30] = "Charlie";
```

Концептуально:

```text
       20
      /  \
    10    30
```

Ключи находятся в отсортированном порядке.

Поэтому `m.find(20)` имеет сложность `O(log n)`, вставка — `O(log n)`, удаление — `O(log n)`.

**Почему дерево должно быть сбалансировано?**

Если сделать обычное бинарное дерево и вставлять:

```text
1
 \
  2
   \
    3
     \
      4
       \
        5
```

получится практически список. Поиск тогда станет `O(n)`.

Сбалансированное дерево старается сохранять высоту около `log₂(n)`, поэтому операции остаются `O(log n)`.

### `std::unordered_map`

`unordered_map` устроен совершенно иначе. В основе — хеш-таблица.

Например:

```cpp
std::unordered_map<std::string, int> ages;

ages["Alice"] = 25;
ages["Bob"] = 30;
```

Упрощённо:

```text
hash("Alice") → 12345
                  ↓
              bucket[5]

hash("Bob") → 67890
                 ↓
             bucket[2]
```

То есть сначала вычисляется hash ключа:

```text
key
 ↓
hash function
 ↓
bucket
 ↓
element
```

**Что такое bucket?**

Хеш-таблица содержит массив «корзин»:

```text
bucket 0 → ...
bucket 1 → ...
bucket 2 → Bob
bucket 3 → ...
bucket 4 → ...
bucket 5 → Alice
bucket 6 → ...
```

Если два ключа попали в одну корзину, возникает collision.

Например:

```text
hash(A) → bucket 3
hash(B) → bucket 3
```

Внутри bucket может быть несколько элементов. Поэтому поиск сначала вычисляет hash, а затем ищет элемент среди кандидатов в соответствующей корзине.

**Почему `unordered_map` обычно быстрее `map`?**

У `map` поиск → `O(log n)`. У `unordered_map` поиск → `O(1)` в среднем. Потому что вместо обхода дерева мы примерно сразу вычисляем `key → hash → bucket`.

Но есть важный нюанс: `unordered_map` не гарантирует `O(1)`. В худшем случае большое количество collision может привести к `O(n)`.

**Главное отличие `map` и `unordered_map`**

```text
map
 ↓
дерево
 ↓
ключи отсортированы
 ↓
O(log n)

unordered_map
 ↓
hash table
 ↓
порядок не гарантирован
 ↓
O(1) average
```

Например:

```cpp
std::map<int, std::string> m = {
    {30, "C"},
    {10, "A"},
    {20, "B"}
};
```

При итерации получим `10, 20, 30`. А `unordered_map` порядок элементов не гарантирует.

**Сравнение на уровне памяти**

```text
vector
┌────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │    │
└────┴────┴────┴────┴────┘
       contiguous

list
[10] ───→ [20] ───→ [30]
 ↑          ↑          ↑
разные места памяти

map
        [50]
       /    \
     [30]   [70]

unordered_map
bucket array
[ ][ ][X][ ][ ][X][ ][ ]
       ↑       ↑
     node    node
```

`vector` — очень хороший cache locality. `list` — плохая locality, плюс каждый узел хранит `prev`/`next`. `map` — много отдельных узлов и указателей. `unordered_map` — есть массив bucket'ов + сами элементы/узлы.

**Что выбирать?**

```text
Нужен обычный динамический массив
        ↓
     vector

Нужны частые вставки/удаления
в середине + есть итератор
        ↓
      list
```

Но `list` стоит использовать осторожно: на практике `vector` часто оказывается быстрее даже там, где теоретически `list` имеет более дешёвую вставку, благодаря cache locality.

```text
Нужны key → value
+ отсортированные ключи
        ↓
      map

Нужны key → value
+ порядок не важен
+ быстрый поиск
        ↓
  unordered_map
```

## 2. Какова сложность основных операций?

Шпаргалка:

```text
vector
└── dynamic array
    ├── [] → O(1)
    ├── push_back → O(1) amortized
    └── contiguous memory

list
└── doubly linked list
    ├── [] → O(n)
    ├── insert/erase по iterator → O(1)
    └── nodes разбросаны по памяти

map
└── balanced BST
    ├── find → O(log n)
    ├── insert → O(log n)
    ├── sorted keys
    └── ordered

unordered_map
└── hash table
    ├── find → O(1) average
    ├── insert → O(1) average
    ├── worst case → O(n)
    └── unordered
```

Самое главное для собеседования: понимать не только Big-O, но и почему она такая: `vector` — арифметика адреса, `list` — переходы по указателям, `map` — обход сбалансированного дерева, `unordered_map` — hash → bucket.

## 3. Когда происходит realloc у `vector`?

У `vector` есть две важные характеристики:

```cpp
v.size();
v.capacity();
```

Например:

```text
size = 4
capacity = 8

┌───────────────────────────────┐
│ 10 │ 20 │ 30 │ 40 │   │   │   │   │
└───────────────────────────────┘
     ←── size ──→
     ←──── capacity ────────→
```

Когда места заканчивается:

```cpp
v.push_back(50);
```

может потребоваться выделить новый больший блок памяти и переместить туда элементы.

Например:

```text
старый:
[10][20][30][40]

        ↓ realloc

новый:
[10][20][30][40][50][ ][ ][ ]
```

Поэтому `push_back()`:

```text
обычно → O(1)
при realloc → O(n)
```

Но в среднем по последовательности операций — амортизированно `O(1)`.

## 4. Что происходит с итераторами после `erase`/`insert`?

Это очень важный вопрос, потому что инвалидация итераторов сильно зависит от контейнера.

Сначала главное: `erase()` может уничтожить элемент, на который указывает итератор, а `insert()`/`push_back()` иногда вообще инвалидирует все итераторы.

Разберём по контейнерам.

### `std::vector`

У `vector` элементы лежат подряд:

```text
[10][20][30][40][50]
     ↑
    it
```

**erase**

```cpp
std::vector<int> v = {10, 20, 30, 40, 50};

auto it = v.begin() + 2; // 30

v.erase(it);
```

После erase:

```text
[10][20][40][50]
```

Итератор `it`, который указывал на удалённый 30, инвалидирован.

Более того, итераторы на элементы после удалённого тоже инвалидируются, потому что элементы сдвигаются:

```text
до:
10  20  30  40  50
        ↑   ↑   ↑
       it   ?   ?

erase(30)

после:
10  20  40  50
        ↑   ↑
      старые итераторы больше нельзя использовать
```

А итераторы до удалённого элемента остаются валидными.

**Важный трюк**

`erase()` возвращает итератор на следующий элемент:

```cpp
it = v.erase(it);
```

Например:

```cpp
for (auto it = v.begin(); it != v.end(); ) {
    if (*it == 30)
        it = v.erase(it);
    else
        ++it;
}
```

Это правильный способ удалять элементы во время обхода.

**`vector::insert`**

Здесь всё зависит от того, произошла ли reallocation.

Если `capacity` хватает:

```cpp
v.insert(it, 42);
```

то итераторы до места вставки остаются валидными, а итераторы от места вставки и дальше инвалидируются.

Если произошло увеличение буфера:

```text
старый буфер
[10][20][30][40]

       ↓ realloc

новый буфер
[10][20][30][40][...]
```

то все итераторы инвалидируются.

То же самое относится к `push_back()`:

```cpp
v.push_back(100);
// если capacity() хватает → итераторы обычно сохраняются;
// если произошла reallocation → все итераторы инвалидированы.
```

### `std::list`

У `list` каждый элемент — отдельный узел:

```text
[10] ↔ [20] ↔ [30] ↔ [40]
```

Поэтому удаление одного элемента не требует перемещения остальных.

```cpp
auto it = ...; // 30

list.erase(it);
```

Получаем:

```text
[10] ↔ [20] ↔ [40]
```

Инвалидируется только итератор на удалённый элемент. Все остальные итераторы остаются валидными.

И вставка:

```cpp
list.insert(it, 42);
```

не инвалидирует существующие итераторы. Это одно из важных преимуществ `list`.

### `std::map`

`map` обычно основан на сбалансированном дереве:

```text
       20
      /  \
    10    30
```

При `insert()` дерево может перестраиваться/балансироваться, но сами узлы элементов не перемещаются как элементы `vector`.

Поэтому `insert` не инвалидирует существующие итераторы, а `erase` инвалидирует только итератор на удалённый элемент.

Например:

```cpp
auto it = m.find(20);

m.erase(it); // it больше использовать нельзя
```

Но итераторы на остальные элементы остаются валидными.

### `std::unordered_map`

Здесь ситуация интереснее из-за rehash.

Например:

```text
bucket 0 → A
bucket 1 → B
bucket 2 → C
```

При добавлении элементов может понадобиться увеличить количество bucket'ов:

```text
старые buckets
[ ][A][ ][B]

       ↓ rehash

новые buckets
[ ][ ][A][ ][B][ ][C][ ]
```

При rehash все итераторы инвалидируются.

`insert` — если вставка вызывает rehash, все итераторы инвалидируются. Если rehash не произошёл — существующие итераторы сохраняются.

`erase` — инвалидируется только итератор на удалённый элемент.

**Шпаргалка**

| Контейнер | `insert` | `erase` |
|-----------|----------|---------|
| `vector` | может инвалидировать часть или все | удалённый + элементы после него |
| `list` | итераторы сохраняются | только удалённый |
| `map` | итераторы сохраняются | только удалённый |
| `unordered_map` | при rehash → все | только удалённый |

**Очень важный момент: erase возвращает следующий итератор**

Это полезно почти для всех контейнеров:

```cpp
it = container.erase(it);
```

Например:

```cpp
for (auto it = m.begin(); it != m.end(); ) {
    if (it->second < 0)
        it = m.erase(it);
    else
        ++it;
}
```

Почему не так?

```cpp
container.erase(it);
++it; // ❌ it уже инвалидирован
```

После `erase(it)` старый `it` использовать нельзя.

**Как это запомнить**

Нужно понимать физическую структуру контейнера:

- `vector` → элементы сдвигаются, возможен realloc → много итераторов могут стать недействительными.
- `list` → элементы отдельными узлами, остальные элементы не двигаются → инвалидируется только удалённый.
- `map` → узлы дерева не перемещаются → инвалидируется только удалённый.
- `unordered_map` → элементы лежат в buckets, `erase` → только удалённый, rehash → все итераторы.

И особенно хорошо помнить три «опасных» случая:

- `vector` → reallocation;
- `unordered_map` → rehash;
- `erase` → итератор на удалённый элемент всегда использовать нельзя.

## 5. Чем `std::set` отличается от `std::unordered_set`?

`std::set` и `std::unordered_set` оба хранят уникальные значения, но внутри устроены по-разному.

Главная разница: `set` → отсортированные элементы + дерево, `unordered_set` → хеш-таблица + порядок не гарантирован.

### `std::set`

Обычно реализован как сбалансированное бинарное дерево поиска (как правило, красно-чёрное дерево).

```cpp
std::set<int> s = {30, 10, 20};
```

При итерации:

```text
10
20
30
```

Элементы автоматически находятся в отсортированном порядке.

Поиск `s.find(20)` — сложность `O(log n)`, вставка `s.insert(40)` — `O(log n)`, удаление `s.erase(20)` — `O(log n)`.

### `std::unordered_set`

Это хеш-таблица.

```cpp
std::unordered_set<int> s = {30, 10, 20};
```

Порядок элементов не гарантирован. Например, при обходе можно получить `20, 30, 10` или другой порядок.

При поиске `s.find(20)` примерно происходит:

```text
20
 ↓
hash(20)
 ↓
bucket
 ↓
элемент
```

Поэтому `find → O(1) average`, `insert → O(1) average`, `erase → O(1) average`.

Но в худшем случае из-за большого количества коллизий — `O(n)`.

**Главное отличие**

| | `std::set` | `std::unordered_set` |
|---|---|---|
| Внутри | Сбалансированное дерево | Хеш-таблица |
| Уникальные элементы | ✅ | ✅ |
| Порядок | Отсортирован | Не гарантирован |
| `find` | O(log n) | O(1) average |
| `insert` | O(log n) | O(1) average |
| `erase` | O(log n) | O(1) average |
| Худший поиск | O(log n) | O(n) |
| Нужен hash | ❌ | ✅ |

**Когда какой использовать?**

`set` — если тебе важно:

```cpp
std::set<int> numbers;

numbers.insert(30);
numbers.insert(10);
numbers.insert(20);
```

получить `10 20 30`. Или нужны операции, связанные с порядком:

```cpp
s.lower_bound(20);
s.upper_bound(20);
```

`unordered_set` — если порядок не имеет значения:

```cpp
std::unordered_set<int> visited;
```

и главное — быстро проверять:

```cpp
if (visited.contains(x)) {
    // уже посещали
}
```

В среднем это `O(1)`.

**Ещё одна важная деталь**

В `set` ключ одновременно является значением:

```cpp
std::set<int>
```

В `map` есть пара `key → value`:

```cpp
std::map<int, std::string>
```

А в `unordered_set` просто набор уникальных ключей:

```cpp
std::unordered_set<int>
```

**Для запоминания**

```text
set
  ↓
tree
  ↓
sorted
  ↓
O(log n)

unordered_set
  ↓
hash table
  ↓
unordered
  ↓
O(1) average
```

Если тебе нужен порядок — `set`. Если порядок не важен, а нужен быстрый поиск — `unordered_set`.

## 6. Как работают хеш-таблицы?

Хеш-таблица — это структура данных, которая позволяет хранить пары ключ → значение и очень быстро находить значение по ключу.

Например:

```text
"alice" → 25
"bob"   → 31
"john"  → 42
```

В C++ её реализацией является, например, `std::unordered_map`.

### 1. Главная идея

Допустим, у нас есть массив:

```text
[0] [1] [2] [3] [4] [5] [6] [7]
```

Нам нужно положить `"alice" → 25`.

Хеш-функция превращает ключ в число:

```text
hash("alice") = 123456
```

Но массив у нас всего из 8 ячеек. Поэтому берём индекс:

```text
123456 % 8 = 0
```

И кладём элемент в bucket 0:

```text
[0] → ("alice", 25)
[1]
[2]
[3]
[4]
[5]
[6]
[7]
```

При поиске `"alice"` происходит примерно то же самое:

```text
"alice"
   ↓
hash("alice")
   ↓
123456
   ↓
123456 % 8
   ↓
bucket 0
   ↓
("alice", 25)
```

Поэтому поиск в среднем очень быстрый — `O(1)`.

### 2. А что если два ключа попали в один bucket?

Это называется коллизия.

Например:

```text
hash("alice") % 8 = 0
hash("bob")   % 8 = 0
```

Оба хотят попасть сюда:

```text
[0]
 ↓
alice → 25
bob   → 31
```

Один из распространённых способов решения — цепочки (chaining).

Условно:

```text
bucket 0
   ↓
┌───────────┐     ┌─────────┐
│ alice: 25 │ →   │ bob: 31 │ → ...
└───────────┘     └─────────┘
```

Тогда при поиске `"bob"`:

```text
hash("bob")
    ↓
bucket 0
    ↓
alice? ❌
    ↓
bob?   ✅
```

Поэтому при большом количестве коллизий поиск может стать медленнее.

### 3. Почему тогда O(1), если приходится искать внутри bucket?

Потому что хорошая хеш-функция старается равномерно распределять ключи.

Например, хорошо:

```text
bucket 0 → 2 элемента
bucket 1 → 1 элемент
bucket 2 → 3 элемента
bucket 3 → 2 элемента
bucket 4 → 1 элемент
...
```

Плохо:

```text
bucket 0 → 1000 элементов
bucket 1 → 0
bucket 2 → 0
bucket 3 → 0
...
```

В среднем цепочки маленькие, поэтому `find → O(1) average`. Но в худшем случае `find → O(n)`, если все ключи оказались в одном bucket.

### 4. Что такое load factor?

Очень важное понятие для понимания `unordered_map`.

Load factor примерно показывает, сколько элементов приходится на один bucket.

Формула:

```text
load_factor = number_of_elements / number_of_buckets
```

Например: 100 элементов, 10 buckets → `load factor = 100 / 10 = 10`. Это много.

А 100 элементов, 200 buckets → `load factor = 100 / 200 = 0.5`. Коллизий потенциально будет меньше.

### 5. Что происходит, когда таблица заполняется?

Хеш-таблица может сделать rehash.

Допустим: 10 buckets, 100 элементов. Становится слишком много элементов.

Тогда создаётся новая таблица, например `10 buckets → 20 buckets`, и все элементы распределяются заново:

```text
старые buckets
      ↓
     rehash
      ↓
новые buckets
```

Почему нужно распределять заново? Потому что индекс зависит от количества bucket'ов:

```text
index = hash(key) % bucket_count
```

Например:

```text
hash = 123

123 % 10 = 3
123 % 20 = 3
```

Иногда индекс совпал, но вообще он может измениться:

```text
hash = 14

14 % 10 = 4
14 % 20 = 14
```

Поэтому элементы нужно перераспределить.

### 6. Как это выглядит целиком

Упрощённая модель:

```text
          key
           │
           ▼
     ┌───────────┐
     │ hash func │
     └─────┬─────┘
           │
           ▼
        hash value
           │
           ▼
       bucket index
           │
           ▼
┌─────────────────────┐
│     hash table      │
│                     │
│ [0] → ...           │
│ [1] → ...           │
│ [2] → key/value     │
│ [3] → ...           │
│ [4] → ...           │
└─────────────────────┘
```

### 7. Как это связано с `std::unordered_map`

Например:

```cpp
std::unordered_map<std::string, int> ages;

ages["Alice"] = 25;
ages["Bob"] = 31;
ages["John"] = 42;
```

Когда пишем `ages["Bob"]`, концептуально происходит:

```text
"Bob"
 ↓
std::hash<std::string>
 ↓
hash value
 ↓
bucket
 ↓
поиск "Bob" внутри bucket
 ↓
31
```

У `std::unordered_map`:

| Операция | Среднее | Худшее |
|----------|---------|--------|
| `find` | O(1) | O(n) |
| `insert` | O(1) | O(n) |
| `erase` | O(1) | O(n) |

При этом rehash может сделать отдельную операцию вставки дорогой, вплоть до O(n), но амортизированно вставки обычно рассматриваются как O(1).

### 8. А `std::unordered_set`?

То же самое, только вместо `key → value` храним только `key`.

Например:

```cpp
std::unordered_set<int> numbers;

numbers.insert(42);
numbers.insert(10);
numbers.insert(100);
```

Концептуально:

```text
hash(42)  → bucket 3
hash(10)  → bucket 7
hash(100) → bucket 2
```

И при `numbers.contains(42)` хеш-таблица быстро определяет, где искать 42.

### 9. Почему `unordered_map` не хранит элементы отсортированными?

Потому что его цель — быстрый поиск по ключу, а не порядок.

Например:

```cpp
std::unordered_map<int, std::string> m{
    {30, "A"},
    {10, "B"},
    {20, "C"}
};
```

При обходе нельзя рассчитывать на `10, 20, 30`.

Если нужен порядок ключей — `std::map`. Если порядок не нужен — `std::unordered_map`.

### 10. Главное отличие `map` и `unordered_map`

Можно представить так:

```text
std::map
          20
         /  \
       10    30
      / \    / \
     ...    ...

Дерево → поиск: O(log n). Зато ключи отсортированы.

std::unordered_map
hash(key)
    ↓
 bucket
    ↓
 element

Хеш-таблица → поиск: O(1) average. Но порядка ключей нет.
```

## 🧠 Для собеседования

Запомни цепочку:

```text
key
 ↓
hash function
 ↓
hash value
 ↓
bucket index
 ↓
bucket
 ↓
element
```

И четыре ключевых понятия:

- **Hash function** — превращает ключ в число.
- **Bucket** — место, куда попадает элемент.
- **Collision** — несколько ключей попали в один bucket.
- **Rehash** — увеличение таблицы и перераспределение элементов.

И главное: хеш-таблица жертвует порядком ради очень быстрого поиска в среднем — `O(1)`.
